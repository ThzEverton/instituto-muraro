# 3. ARQUITETURA GERAL

O sistema seguirá a arquitetura:

```text
USUÁRIO
   │
   ▼
FRONTEND REACT
   │
   ▼
API REST /api/v1
   │
   ▼
FASTIFY ROUTES
   │
   ▼
CONTROLLERS
   │
   ▼
SERVICES
   │
   ▼
REPOSITORIES
   │
   ▼
PRISMA ORM
   │
   ▼
POSTGRESQL
```

## Responsabilidades

**View:** componentes React, páginas, formulários, calendário, tabelas e dashboards.

**Controller:** recebe requisições, extrai informações validadas, chama os Services e devolve respostas HTTP.

**Service:** concentra regras de negócio, transações, validações de domínio e verificações de autorização.

**Repository:** centraliza consultas, filtros e persistência utilizando Prisma.

**Model:** representa entidades, relacionamentos e estruturas do domínio.

## Regras arquiteturais

- Não colocar regras de negócio dentro dos Controllers.
- Não executar consultas Prisma diretamente nas rotas.
- Não colocar regras de autorização apenas no frontend.
- Não duplicar regras de disponibilidade em diversos módulos.
- Não duplicar schemas de formulários.
- Não misturar responsabilidades clínicas com componentes administrativos.
- Não acessar diretamente o banco pelo frontend.
- Utilizar injeção de dependências simples e tipada quando necessário.
- Criar interfaces e tipos compartilhados por contratos OpenAPI.

# 7. BACKEND — REGRAS GERAIS

**Base URL:**

`/api/v1`

**Desenvolvimento:**

`http://localhost:3333/api/v1`

**Swagger:**

`http://localhost:3333/docs`

## Padrões

- JSON nas operações comuns.
- Multipart para upload.
- UUID para identificadores.
- ISO 8601 para datas e horários.
- UTC no armazenamento.
- America/Sao_Paulo para regras locais e exibição.
- Valores monetários em centavos.
- Paginação nas listagens.
- Filtros e ordenações validados.
- Schemas Zod.
- Respostas padronizadas.
- Logs estruturados.
- Autorização por endpoint e por recurso.

## Resposta individual

```json
{
  "data": {
    "id": "uuid"
  }
}
```

## Resposta de listagem

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 0,
    "totalPages": 0
  }
}
```

## Erros

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Dados inválidos.",
    "details": [],
    "requestId": "req_123"
  }
}
```

Utilizar códigos HTTP corretos, incluindo 200, 201, 204, 400, 401, 403, 404, 409, 422, 429 e 500.

## Regras do banco

- Utilizar chaves estrangeiras.
- Criar índices para pesquisas frequentes.
- Criar índice em `patientId`.
- Criar índice em `professionalId`.
- Criar índices para data e status dos agendamentos.
- Garantir unicidade de e-mail dos usuários.
- Evitar exclusão física de registros clínicos.
- Preservar histórico financeiro.
- Utilizar transações para operações relacionadas.
- Criar migrations versionadas.

Criar constraints e verificações para impedir valores monetários negativos, intervalos inválidos e referências inconsistentes.

## Concorrência

A agenda precisa evitar que duas requisições simultâneas reservem o mesmo horário.

Não depender exclusivamente de:

1. Consultar disponibilidade.
2. Verificar que está livre.
3. Inserir agendamento.

Essa sequência isolada pode permitir conflitos concorrentes.

Implementar controle transacional de concorrência por profissional e intervalo, utilizando os recursos adequados do PostgreSQL.

Considerar restrições de sobreposição no banco e tratamento dos bloqueios dentro da mesma estratégia de consistência.

## Requisitos

- Senhas com hash seguro.
- Argon2id ou algoritmo equivalente adequado.
- Cookies HttpOnly.
- Secure em produção.
- SameSite configurado.
- Tokens com expiração.
- Renovação de sessão.
- Revogação de sessão.
- Proteção CSRF.
- Rate limiting.
- Mensagens de erro sem revelar a existência de contas.
- Logs de tentativas relevantes.
- Proteção contra força bruta.

## Perfis

```typescript
type Role =
  | "ADMIN"
  | "RECEPTION"
  | "PROFESSIONAL";
```

O frontend poderá ocultar menus por perfil, mas a API deverá verificar toda autorização.

## Regras clínicas

O administrador não deverá ter acesso automático a prontuários apenas por possuir perfil administrativo.

O profissional deverá possuir autorização específica para acessar os registros de um paciente.

A recepção não deverá consultar o conteúdo clínico.

Implementar essas verificações no Service Layer, com políticas centralizadas e verificáveis.

# 12. BACKEND — MOTOR DE DISPONIBILIDADE

Criar um Service dedicado:

`AvailabilityService`

Esse serviço será responsável por determinar horários realmente disponíveis.

## Dados considerados

1. Expediente semanal.
2. Exceções de expediente.
3. Almoço.
4. Bloqueios avulsos.
5. Bloqueios recorrentes.
6. Férias.
7. Feriados configurados.
8. Agendamentos existentes.
9. Duração do serviço.
10. Status dos eventos.
11. Fuso horário.

## Endpoint

`GET /appointments/availability`

Parâmetros:

- professionalId.
- serviceId.
- date.

## Exemplo de resposta

```json
{
  "data": {
    "date": "2026-10-26",
    "professionalId": "uuid",
    "slots": [
      {
        "startsAt": "2026-10-26T08:00:00-03:00",
        "endsAt": "2026-10-26T08:50:00-03:00"
      },
      {
        "startsAt": "2026-10-26T09:00:00-03:00",
        "endsAt": "2026-10-26T09:50:00-03:00"
      }
    ]
  }
}
```

## Algoritmo

1. Buscar configuração semanal.
2. Aplicar exceções.
3. Montar intervalos de expediente.
4. Subtrair bloqueios.
5. Subtrair agendamentos que ocupam horário.

Antes da implantação:

1. Identificar o sistema atual.
2. Verificar formas de exportação.
3. Identificar pacientes.
4. Identificar profissionais.
5. Identificar agendamentos futuros.
6. Identificar documentos.
7. Avaliar prontuários históricos.
8. Avaliar dados financeiros.
9. Planejar importação.
10. Executar testes de integridade.

A migração complexa de dados históricos não deve ser presumida como incluída sem avaliação.

O sistema anterior só deverá ser desativado após validação da continuidade dos registros e das obrigações de guarda.

O sistema só poderá ser considerado tecnicamente concluído quando:

- Frontend navegar corretamente.
- API REST estiver implementada.
- PostgreSQL persistir os dados.
- Prisma migrations funcionarem.
- Login real estiver implementado.
- Permissões forem aplicadas no backend.
- Pacientes tiverem CRUD completo.
- Profissionais tiverem CRUD completo.
- Serviços tiverem CRUD completo.
- Agenda funcionar.
- Bloqueios impedirem conflitos.
- Almoço recorrente funcionar.
- Férias funcionarem.
- Reagendamentos preservarem histórico.
- Sessões recorrentes funcionarem.
- Anamneses puderem ser criadas e respondidas.
- Links individuais funcionarem.
- Questionários tiverem expiração e revogação reais.

# 37. LIMITES DO PROJETO

Não incluir automaticamente:

- Aplicativos nativos Android e iOS.
- WhatsApp Business API.
- Chatbot.
- Mensagens automáticas.
- Pagamento online.
- Emissão de notas fiscais.
- Integrações bancárias.
- Integrações com convênios.
- Relatórios avançados não previstos.
- Migração complexa de históricos.
- Funcionalidades clínicas específicas ainda não aprovadas.

Esses recursos poderão ser avaliados separadamente.

**Investimento preliminar de referência:** R$ 6.900.

**Manutenção mensal sugerida:** R$ 397.

Esses valores não constituem aprovação definitiva do escopo ampliado. O esforço técnico, a implantação, os requisitos clínicos, a migração e a operação precisam ser dimensionados antes do compromisso comercial.
