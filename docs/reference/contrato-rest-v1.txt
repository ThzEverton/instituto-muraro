# 1. Regras gerais da API

### Endereços

**Desenvolvimento:**
`http://localhost:3333/api/v1`

**Produção:**
`https://sistema.institutomuraro.com.br/api/v1`

O domínio de produção é ilustrativo e será configurado posteriormente.

**Documentação Swagger:**
`http://localhost:3333/docs`

### Padrões obrigatórios

- Comunicação por HTTPS em produção.
- Requisições e respostas JSON, exceto upload e download de arquivos.
- Endpoints organizados por recurso.
- IDs no formato UUID.
- Datas de calendário no formato `YYYY-MM-DD`.
- Data e hora em ISO 8601, com fuso horário.
- Datas armazenadas em UTC.
- Fuso horário padrão: `America/Sao_Paulo`.
- Valores monetários representados em centavos, usando números inteiros.
- Paginação nas listagens.
- Respostas de erro padronizadas.
- Autorização no backend, independentemente das permissões exibidas no frontend.

### Resposta de listagem

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 0,
    "totalPages": 0
  }
}
```

### Resposta individual

```json
{
  "data": {
    "id": "uuid"
  }
}
```

### Resposta de erro

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Os dados informados são inválidos.",
    "details": [
      {
        "field": "fullName",
        "message": "Campo obrigatório."
      }
    ],
    "requestId": "req_123"
  }
}
```

**Códigos HTTP:**

- `200` — Consulta ou atualização realizada.
- `201` — Recurso criado.
- `204` — Operação concluída sem conteúdo.
- `400` — Requisição inválida.
- `401` — Usuário não autenticado.
- `403` — Acesso não autorizado.
- `404` — Recurso não encontrado.
- `409` — Conflito de dados ou de horários.
- `422` — Regra de negócio ou validação não atendida.
- `429` — Limite de requisições excedido.
- `500` — Erro interno.

Os erros devem possuir códigos estáveis, para que o frontend consiga tratá-los e apresentar mensagens adequadas.

# 2. API de autenticação

**Prefixo:** `/auth`

| Método | Endpoint | Função |
|---|---|---|
| POST | `/auth/login` | Realizar login |
| POST | `/auth/refresh` | Renovar sessão |
| POST | `/auth/logout` | Encerrar sessão |
| GET | `/auth/me` | Obter usuário autenticado |
| PATCH | `/auth/password` | Alterar senha |

### POST /auth/login

**Request:**

```json
{
  "email": "admin@exemplo.com",
  "password": "senha-de-exemplo"
}
```

**Response:**

```json
{
  "data": {
    "user": {
      "id": "uuid",
      "name": "Administrador",
      "email": "admin@exemplo.com",
      "role": "ADMIN",
      "professionalId": null,
      "active": true
    }
  }
}
```

O backend estabelecerá a sessão por cookies seguros, HttpOnly e SameSite, com estratégia de renovação e proteção contra CSRF. Tokens de acesso e renovação não devem ser armazenados em `localStorage`.

### Perfis do sistema

```typescript
type UserRole =
  | "ADMIN"
  | "RECEPTION"
  | "PROFESSIONAL";
```

**Regras:**
- Não haverá cadastro público de usuários.
- Somente administradores poderão cadastrar colaboradores.
- As permissões serão verificadas em cada requisição.
- Um profissional não poderá consultar prontuários de outros pacientes sem autorização.
- O administrador não terá automaticamente acesso irrestrito aos registros clínicos.

# 8. API de WhatsApp manual

Não haverá integração com a API do WhatsApp.

O backend apenas fornecerá os dados para uma mensagem pré-preenchida.

### GET /appointments/:id/whatsapp-draft

**Query param:**

```text
?type=CONFIRMATION
```

Tipos:

```typescript
type WhatsAppDraftType =
  | "CONFIRMATION"
  | "REMINDER"
  | "CANCELLATION";
```

**Response:**

```json
{
  "data": {
    "phoneE164": "+5518999999999",
    "message": "Olá, Maria! Aqui é do Instituto Muraro. Seu atendimento está agendado para 26/10 às 14h. Podemos confirmar sua presença?"
  }
}
```

O frontend montará o link `https://wa.me/5518999999999?text=...` utilizando `encodeURIComponent`.

O envio dependerá da ação manual do colaborador no WhatsApp.

**Não haverá:**
- Envio automático.
- Leitura de mensagens.
- Sincronização de respostas.
- Chatbot.
- Webhook do WhatsApp.
- Armazenamento de sessão do WhatsApp Web.


### Segurança dos formulários públicos

- Token aleatório de alta entropia.
- Prazo de expiração.
- Uso único após envio.
- Token armazenado de forma protegida no backend.
- Validação dos campos enviados.
- Limitação de tentativas.
- Nenhum prontuário anterior exposto no link.
- Verificação adicional da identidade do destinatário, quando necessária.
- Preservação das respostas originais após envio.

As respostas deverão ficar disponíveis somente para profissionais autorizados.

```json
{
  "appointmentId": "uuid",
  "professionalId": "uuid",
  "evolution": "Registro de evolução clínica...",
  "observations": "Observações complementares..."
```

O profissional responsável será validado pelo backend a partir da sessão autenticada, não apenas do identificador enviado pelo frontend.

### Modelo de prontuário

- Cada registro deverá identificar o autor.
- Consultas e alterações relevantes deverão ser auditadas.
- O acesso deverá depender de autorização clínica específica.
- O frontend não poderá utilizar dados de prontuário sem autenticação apropriada.

## 12.4 Resumo financeiro

`GET /finance/summary`

**Query params:**

```text
?from=2026-10-01
&to=2026-10-31
```

**Response:**

```json
{
  "data": {
    "revenueCents": 1500000,
    "expenseCents": 350000,
    "outstandingCents": 200000,
    "balanceCents": 1150000
  }
}
```

### Regras financeiras

- Valores sempre em centavos.
- Movimentações relevantes auditadas.
- Não permitir pagamento superior ao saldo da cobrança sem regra explícita.
- Permitir pagamentos parciais.
- Separar pagamentos recebidos de valores ainda pendentes.
- Resumo calculado pelo backend.
- Não emitir nota fiscal.
- Não realizar cobrança automática.
- Não integrar bancos ou adquirentes no MVP.

# 20. Como desenvolver o frontend agora

## Modo MOCK

O frontend deverá funcionar inicialmente sem backend ativo, utilizando dados fictícios.

Criar mocks para:

- Usuários e perfis.
- Pacientes.
- Profissionais.
- Serviços.
- Horários disponíveis.
- Agendamentos.
- Modelos de anamnese.
- Respostas de anamnese.
- Registros clínicos fictícios.
- Cobranças.
- Pagamentos.
- Despesas.
- Indicadores do dashboard.

Utilizar MSW para interceptar as chamadas HTTP durante o desenvolvimento.

Os mocks deverão reproduzir os mesmos contratos, códigos HTTP e cenários de erro previstos na API real.

## Modo API

Quando o backend estiver disponível, o frontend deverá utilizar a mesma camada de serviços e os mesmos tipos, substituindo apenas a origem das respostas.

Variável de ambiente:

`VITE_API_URL=http://localhost:3333/api/v1`

Em produção, preferir `/api/v1` na mesma origem da aplicação, usando o proxy Caddy.

# 22. Instrução para o desenvolvedor frontend

Desenvolva o frontend do Sistema de Gestão Clínica Instituto Muraro utilizando React, Vite, TypeScript, Tailwind CSS, shadcn/ui e TanStack Query.

Utilize integralmente os contratos REST descritos nesta especificação.

Inicialmente, desenvolva todas as interfaces com dados simulados por MSW. Não exija conexão com o PostgreSQL ou com uma API real durante a montagem das telas.

Crie uma camada de serviços isolada da interface, permitindo substituir os mocks pela API Fastify sem reescrever componentes.

Organize as telas por módulos, utilizando layouts reutilizáveis, formulários validados, tratamento de loading, estados vazios, erros e feedback visual das operações.

Implemente:
- Dashboard administrativo.
- Agenda diária, semanal e mensal.
- Cadastro e gerenciamento de pacientes.
- Cadastro e gerenciamento de profissionais.
- Cadastro de serviços.
- Agendamentos e controle de status.
